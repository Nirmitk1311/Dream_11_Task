01 — Problem statement & product context

Problem to solve: After joining a fantasy cricket contest and locking a team, fans can see their current points/rank, but a leaderboard alone doesn't answer: “Which upcoming events help me?”, “Which unselected players could hurt my rank?”, and “What happens if my captain takes a wicket or hits a six?”

The proposed product converts static fantasy standings into personalized, scenario-based explanations. It is a proposed gap rather than a verified absence of an existing internal Dream11 feature. Validate with fans and platform owners.

Important current-market context: Dream11 announced an August 27, 2026 shift to a global AI-first sports engagement platform with social contests and no prizes. Build for non-cash fan engagement; do not design a gambling/reward optimization product. Dream11 already has AI functionality, so the differentiation is explainable, individual-contest scenario impact.

Primary outcome: A fan understands why their rank changed and what realistic on-field events could affect their relative standing. Secondary: deeper match engagement and fewer confusing leaderboard moments.

02 — Target user & core scenario

Target fan

A cricket fan who has already joined a Dream11-style fantasy contest, selected 11 players, marked a captain (2×) and vice-captain (1.5×), and is now following an in-progress T20 match. Their regular contest team is assumed locked.

Fan frustration

They jump between a scorecard, team points, and leaderboard without understanding whether a boundary by their captain helps enough to overtake nearby competitors—or whether an unselected bowler is dangerous.

Core user story

As a fantasy contestant, I want to test plausible next-ball and next-over scenarios and instantly see the impact on my points and estimated contest standing, so that I can follow the match through my own team's perspective.

Example, purely fictional

At 14.2 overs, user has 450 points and ranks #8,450. They click “What if my captain hits a six?” The product computes a rule-based point delta, applies the captain multiplier, recalculates scores for a sample simulated leaderboard, and explains the resulting rank. It must not claim this is a real Dream11 rank.

03 — Features (prioritized)

P0 • What-if rank simulation

Choose an active player and an event (dot ball, run, four, six, wicket, catch). Show point delta, before/after points, and before/after rank for a known demo leaderboard.

P0 • Transparent explanation

Explain exactly why points changed and why rank shifted (captain multiplier, relative gains of competitors, ties). Include event and rules references; no invented facts.

P1 • Threat detector

Highlight unselected players appearing on high-ranking opponent teams. Estimate how their favorable performances could harm the user's standing. Label based on available lineup sample.

P1 • Personalized alerts

For replayed ball events, alert when the user's projected points/rank or key threats change substantially; let fans configure an alert threshold.

P2 • Natural-language scenarios

User asks “If my vice-captain takes 2 wickets, can I reach top 100?” Parser converts the request into validated, structured events before calling deterministic simulation.

P2 • Uncertainty-aware forecasts

Monte Carlo sampling from historical rates can yield rank distributions and intervals, not guaranteed rank predictions. Clearly separate forecasts from what-if calculations.

04 — The exact MVP to build first

  1. Load one historical T20 match snapshot and a roster of 22 plausible players. Demo data may be fictional, but must be unambiguously labeled; do not fabricate an actual match.
  2. Provide one predefined 11-player fantasy team including captain and vice-captain, plus the ability to switch captain and vice-captain in demo setup only.
  3. Generate at least 100 deterministic simulated competing fantasy lineups using seeded randomness and legal/defined team constraints for the selected demo format.
  4. Show current team points + rank within that simulated contest.
  5. Offer event buttons: 1 run, four, six, dot ball, wicket, catch. On click, apply the correct event to one player and re-score all affected lineups, not only the user's team.
  6. Present a short fan-centric explanation, with a clear rule breakdown: “Six scored → batting runs + six bonus → captain multiplier = X additional fantasy points. Competitors owning the same captain also benefit.”
  7. Include Reset, Next ball for replay mode, and visibly labeled simulation / data-source badges.
Critical: If there is no authorized access to Dream11's live contests or opponents' lineups, all demo leaderboard ranks MUST be marked Simulated. Never scrape private user accounts, bypass access controls, or imply official integration.

05 — Scoring and rank logic

Implement scoring with a pure deterministic rules engine; use an LLM only to parse questions and phrase verified results. The official page supports multiple formats with different rules. Choose a specific T20 ruleset and store its version/config; do not blend formats.

player_points = score_events(player_event_history, scoring_ruleset) team_points = SUM(player_points[player_id] * multiplier[player_id]) multiplier = 2 for captain, 1.5 for vice-captain, 1 otherwise for each scenario: clone current match state validate scenario (eligible player, legal/meaningful event, no impossible stats) apply events to cloned state recompute scoring for every affected player and lineup sort all contestant totals descending compute user rank with explicit tie strategy return before/after points, rank, impacted teams, and rule breakdown

Engineering notes

  • A six is not automatically only +6 points: a format may grant runs plus a six bonus. Apply the exact selected ruleset, without hardcoding an unverified 12-point delta.
  • Dot-ball point belongs to the bowler where applicable; a six might change bowler economy as well as batter score. Recompute derived stats and milestone/threshold bonuses.
  • Batting, bowling and fielding events can update more than one player; dismissal type and extras matter.
  • Milestone and strike-rate/economy effects should be derived from the entire updated match state to avoid double counting.
  • Handle points revisions, substitutes, abandoned games, inning limits, and format-specific edge cases in later iterations.
  • Rank should be defined with a documented tie convention. Show “rank in simulated group”, not the real contest rank.
  • For Monte Carlo forecasts, show distributions and assumptions; a single what-if scenario is not a probability forecast.

07 — Engineering architecture

Frontend: React + TypeScript + Vite (or Next.js) with mobile-first dark dashboard.

Backend: Python FastAPI or TypeScript server; scenario simulator and scoring engine kept independent from presentation.

State: Local seeded JSON for initial deliverable; PostgreSQL/Redis only after the prototype works.

AI: Optional LLM endpoint. Use a structured schema to translate natural-language prompts into supported events. Reject ambiguous/impossible scenarios; generate grounded descriptions from scorer-produced JSON. Provide fully functional deterministic explanation templates when API keys are missing.

Live data: Architecture supports a future licensed feed behind an adapter; use historical replay until integration permission is available.

Historical match / licensed future feed → normalized event store ↓ scoring rules engine ↓ User lineup + simulated competitor lineups → scenario / rank engine ↓ structured numeric output ↓ explanation templates / LLM ↓ dashboard + insight cards

08 — UI / interaction design

Desktop and phone: show a match header (teams, score, over, replay status); top KPIs (my points, simulated rank, position movement); my XI panel (C/VC clearly displayed); scenario bar (player, event, simulate); live explanation card; competitor threat list; replay controls.

Suggested dark visual theme with green accent; avoid copying protected logos or claiming Dream11 endorsement. Product name for prototype: Fantasy Copilot, with subtitle “Independent concept for Dream11-style contests”.

Use approachable cricket language. Good alert: “Your captain's six moves you up 12 positions in this simulated league—many nearby teams also own him.” Bad alert: “AI guarantees you will reach top 100.”

What to measure in a user trial

  • Task success: can users correctly answer “which event helps me?” after using the tool?
  • Explanation accuracy against rules engine and event history; target zero unsupported numerical claims.
  • Time to understand a ranking change.
  • Share of users who launch a second scenario / return during the same match.
